Ingeniería del Modelo Analítico

Calcular la frecuencia real de los clientes en entornos corporativos exige superar graves sesgos estadísticos. A continuación, presento los 6 retos arquitectónicos resueltos para este proyecto empleando SQL / Tableau Level of Detail (LOD).

01. Agregación

La "Falsa" Frecuencia Promedio

El Conflicto: Al intentar calcular la frecuencia mediante promedios simples de facturas, se generaban agregaciones erróneas que no reflejaban el comportamiento individual por cliente, sino un volcado general global distorsionado.

Resolución: Implementé Expresiones de Nivel de Detalle (LOD) para etiquetar estáticamente a cada cliente individual con su volumen de facturas únicas antes de inyectarlas en el promedio poblacional.

// Compras totales bloqueadas por cada cliente único
{ FIXED [Email Cliente] : COUNTD([Numero Factura]) }
02. Gobierno de Datos

El Identificador Único Absoluto

El Conflicto: La data transaccional venía sin limpieza de los sistemas Core. Requeríamos asegurar que la frecuencia no contara facturas duplicadas artificialmente (ej. por múltiples líneas de productos en una sola orden).

Resolución: Se desarrolló un campo de validación cruzada mediante manipulación asimétrica de cadenas (string manipulation) que extrae la pureza del ticket omitiendo variables nulas o decimales espurios.

[Email Cliente] + 
LEFT(STR([Numero Pedido]), LEN(STR([Numero Pedido])) - 2) + 
STR([Fecha Pedido])
03. Flexibilidad Analítica

Ecosistema Temporal Dinámico

El Conflicto: La Dirección General requería analizar la frecuencia en "lentes" distintos (Anual, Semestral, Trimestral) desde un único panel maestro, forzando al motor a adaptar el denominador geométricamente.

Resolución: Se codificó un selector paramétrico robusto capaz de mutar la granularidad temporal al vuelo.

// 1. Matriz de Periodo Dinámico
CASE [Elegir Periodo]
   WHEN "Año" THEN STR(YEAR([Fecha]))
   WHEN "Semestre" THEN STR(YEAR([Fecha])) + IF MONTH([Fecha]) <= 6 THEN " S1" ELSE " S2" END
   WHEN "Trimestre" THEN STR(YEAR([Fecha])) + "-Q" + STR(DATEPART('quarter', [Fecha]))
END

// 2. Ejecución LOD contra la Variación Temporal
{ FIXED [Email Cliente] : COUNTD([ID_Factura_Unico]) } / 
{ FIXED [Email Cliente] : COUNTD([Periodo Dinamico]) }
04. Medición de Intervalos

El Ritmo de Compra (Inter-purchase Time)

El Conflicto: Saber cuántas compras hace un cliente informa el Lifetime Value (LTV), pero no el "espacio vital" entre ellas. Debíamos medir los espacios vacíos evitando colapsos matemáticos (división por cero) en usuarios pioneros de solo una compra.

Resolución: Segmentación matemática midiendo N-1 transacciones respecto a los extremos de sus compras vitalicias.

DATEDIFF('day', {FIXED [Email Cliente]: MIN([Fecha])}, {FIXED [Email Cliente]: MAX([Fecha])}) 
/ 
({FIXED [Email Cliente]: COUNTD([ID_Factura_Unico])} - 1)
05. Sesgo Estadístico

El Defecto de los Racimos (Clustering)

El Conflicto: Analíticamente, un usuario realizando 5 tickets fragmentados el mismo día ocasionaba que el "Ritmo" arrojara una ilusión de recurrencia masiva (una vez cada pocos días), ocultando que históricamente el cliente visita la tienda una vez cada 3 meses.

Resolución: Transición absoluta del enfoque de "Transacciones" a "Días de Visita Real", validando así recurrencia en sustratos geolocalizados válidos.

// Ritmo Real del Customer Journey
DATEDIFF('day', MIN([Fecha]), MAX([Fecha])) / (COUNTD([Fecha]) - 1)
06. Control de Daños

Depuración de Outliers Institucionales

El Conflicto: Distorsión de promedios causada por facturas huérfanas o entidades institucionales simulando ser "clientes finales" con historiales de compras que superaban los 14,000 registros.

Resolución: Inyección de reglas de negocio para depurar Outliers institucionales y proteger la jerarquía, usando Filtros de Contexto de motor profundo para que los filtros funcionen estáticamente antes de las cláusulas FIXED.

Impacto Corporativo: Al neutralizar el sesgo, la proyección predictiva sobre retención y reactivación de clientes de verdadero volumen incrementó su rentabilidad drásticamente.
